# Commands

`awb` is the one command of the Architect Workbench. Exit codes: 0 ok, 1 findings or a file withheld, 2 usage or error.
`awb <command> --help` shows the options of any command.

Two sides. The owner side holds the register of names and the originals and is run by you in your own shell. The
work side is what Workbench sessions (and you) run inside `tcp-` projects. A name is only ever typed on the owner
side.

## The doors

Customer material has one door per kind. The window is where you type: your own terminal as the owner, or the
session of the project.

| the material | the command | the window | what comes out |
|---|---|---|---|
| a file from a mail | `awb import tcp-xxxx FILE` | your own terminal | a copy in `~/tcp-shared/outbox/CUST-XXXX/` (for a project without a customer `~/tcp-shared/outbox/tcp-xxxx/`) named by the vault's file id and the suffix; the customer as its code, every other person, company, place and name as a token (`[person 1]`, `[company 1]`, `[place 1]`, `[name 1]`) |
| a mail text | `pbpaste \| awb import tcp-xxxx --paste --kind mail` | your own terminal | `mail-<date>-<n>.md`; signature and quoted headers wiped to `[signature]` and `[mail header] from [person 2] to [person 1]`; person, company, place, mail address and phone as tokens; a secret refuses the whole paste |
| a meeting transcript | `pbpaste \| awb import tcp-xxxx --paste --kind transcript` | your own terminal | `transcript-<date>-<n>.md`; each speaker `[person 1]`, `[person 2]`; the filler lines of the meeting tool dropped |
| a spreadsheet | `awb import tcp-xxxx FILE`, or for text copied from it `pbpaste \| awb import tcp-xxxx --paste --kind table` | your own terminal | for a file as above; for a paste `table-<date>-<n>.csv` with a column of people, mail addresses, phones, companies or places wiped as a whole column |
| a vendor image or a screenshot | `awb inbox take WORDS...` from the lab inbox | the session | the file itself after the name check, in `input/` and the project's `in/`; a picture in customer material is not copied, it stays held (`awb images`) |
| a file of the lab without customer content | `awb inbox take WORDS...` from the lab inbox | the session | the file itself after the name check; a registered name holds it |
| a customer file already in the project's `in/` folder of the bucket | `awb import tcp-xxxx` (all new files of `in/`), or `awb inbox take WORDS...` | your own terminal, or the session | as for a file from a mail; the session gets the sanitised copies of your intake in wipe mode, never the original |

`awb bucket pull CODE` (new files of `in/` into the vault inbox, then the intake) is a part of `awb import`.
`awb intake` (the wipe alone, over the vault inbox or the FILE arguments) is a part of `awb import`. Nobody runs either by hand.

## Owner side (your own shell, never through a session)

| command | what it does |
|---|---|
| `awb start project\|query --goal "..." [--customer new] [--tag TAG]... [--from DIR [--trusted]]` | a piece of work in one command: register, spawn, grant, import, then the line `open: awb projects open tcp-xxxx`. `--customer new` issues the project code and the customer code from the same four characters (`tcp-xxxx` and `CUST-XXXX`; a pair of which either code is taken is drawn again); `--customer CUST-XXXX` is refused with one line, every project gets its own code, ten projects for one customer are ten codes that are never linked; a customer without a registered form is asked for its written forms on the terminal, one per line, an empty line ends, as `awb import` asks; an empty first line issues the codes without any form (a fully anonymous project). The spawn runs as the work user through `sudo -n` as `awb projects open` does (on a host without a work user in this process); then your grant `awb projects kind CODE KIND`; then `awb import CODE` for the new files of the project's `in/` folder of the owner bucket (the vault inbox is never taken here, it may hold another customer's files). `--from DIR` replaces that last step: `awb import CODE` runs inside the start on every regular file of DIR and its subfolders (a link or a special file is skipped and counted; an empty or missing folder is refused before anything is made), with `--trusted` when you give it (an export that carries no name), and the run ends with the one line `app: SSH host awb-10491, folder WORKHOME/tcp-xxxx` (the folder is the project's folder of the register) after the open line. Without `--from` nothing changes. A step that fails stops the run and says which steps are done. Your own terminal only |
| `awb init` | create `~/tcp-shared`, `~/tcp-vault` and an empty register (done once) |
| `awb import tcp-xxxx [FILE...]` | the one door for customer material: takes the FILE arguments, else every new file of the project's `in/` folder in the bucket, else everything in `~/tcp-vault/inbox`, and runs the intake for the project's customer in wipe mode. The copies go to `~/tcp-shared/outbox/CUST-XXXX/` (for a project without a customer to `~/tcp-shared/outbox/tcp-xxxx/`, with no customer code) and carry the customer as its code and every other name the rules recognise as a token (`[person 1]`, `[company 1]`, `[place 1]`, `[name 1]`, numbered within the import); nothing stops, no editor opens. It prints the files taken, the copies written, the values wiped per class, the pictures held and the files withheld, never a name, and the sessions of the project read "new input" at their next prompt. Your own terminal only |
| `awb import tcp-xxxx --customer CUST-XXXX` or `--customer new` | only when a project without a customer is to get one (without it such a project imports with no customer code): `new` issues `CUST-` and the project's four characters (refused when that code is taken: the project keeps its code, so there is no second one to draw). A customer without a registered form is asked for its written forms on the terminal, one per line, an empty line ends; for a project without a customer an empty first line issues the code without a form |
| `awb import tcp-xxxx --redo` | the repair of a wiped term: after `awb register keep "the term"`, the originals of the customer's last import run again from the vault and the copies replace the earlier ones under the same file ids; the session reads "replaced" |
| `awb import --auto` | the owner's job of the timer `awb-import-auto` (every 2 minutes): the new files of `in/` of every active project whose import is not running; a clean copy of `awb clean` (`*.clean.md`, `*.clean.log` ...) with `--trusted`, any other file in wipe mode; the original into the vault and out of `in/` (the key service's `bucket_drop_in`, a file of `in/` of an active project only), the "new input" notice (the session of the project reads `new input: N files (FILE IDS)` at its next prompt, once), one line per run in the journal and in `~/tcp-vault/import-auto.log` with codes and counts. A project whose customer has no form yet stays for `awb import CODE` in your own terminal. Every import holds the lock of its project, so a second one at the same time is refused with one line |
| `awb import tcp-xxxx --trusted [FILE...]` | you vouch that the files hold no name (your own anonymous material): no name is guessed, so technical words stay as they are; registered forms, secrets (also a password written in prose), mail addresses and phones are still wiped; with `--redo` it redoes the last import that way |
| `awb import tcp-xxxx --review` | the rare case where a person, a partner or a place must keep a code: the run stops once, an editor opens with the candidates (`p` person, `o` company, `c` this customer, `s` place, `+` one more form, `-` later, no mark: keep), then it goes on in wipe mode and a candidate left for later is a token |
| `awb vault show` | the newest private report (what was wiped, by class and rule, and the forms the run learned) of `--customer CUST-XXXX` or of the only customer with a report of the last day; a FILE shows that file. Your own terminal only, never to a pipe or inside an assistant session |
| `awb import tcp-xxxx --paste [--kind mail\|transcript\|table]` | the same one door for text you copy from a mail client, a meeting tool or a spreadsheet: the text comes on standard input (`pbpaste \| awb import tcp-xxxx --paste`, `wl-paste` or `xclip -o -selection clipboard` on Linux) or paste into the terminal and end with Ctrl-D with nothing shown and is never printed. It runs through the intake of the project's customer in wipe mode: the customer's forms become its code and every other person, company, place, mail address and phone a token. A secret (a key, a token, a password line) refuses the whole paste with its class and line number and writes nothing. The copy goes to the outbox like an imported file (`~/tcp-shared/outbox/CUST-XXXX/`, for a project without a customer under the project code), the sessions of the project read "new input" at their next prompt. The reports are written as for a file. The paste itself is not kept, so `--redo` does not take it again: paste it again after `awb register keep`. It prints the kind, the lines, the name of the copy and the values wiped per class. It takes no FILE, `--customer`, `--review` or `--redo`. Your own terminal only: a work session and the work user get `held: a pasted mail or transcript goes in through awb import tcp-xxxx --paste in your own terminal` |
| `--kind mail` | the copy is `mail-<date>-<n>.md`. A signature block (from a closing such as Best regards or Mit freundlichen Grüßen or from a line `--` to the next quoted header or the end, 25 lines at most) is wiped as a whole to the line `[signature]` and the token of its signer. Every quoted chain header (an `On ... wrote:` line, `-----Original Message-----`, a block of From, Sent, To and Subject lines) to the line `[mail header] from [person 2] to [person 1]` with no date, subject or address. A signature inside a quoted answer goes the same way |
| `--kind transcript` | the copy is `transcript-<date>-<n>.md`. Each speaker becomes `[person 1]`, `[person 2]` within the paste, numbered by the first turn, also where the name is spoken; timestamps stay; the filler lines of the meeting tool (who joined or left, recording started, a generated-by line, a cue number) are dropped |
| `--kind table` | the copy is `table-<date>-<n>.csv`. The text is tab-separated as a spreadsheet copies it and keeps its columns; a column whose header names people or mail addresses (also phones, companies and places) is wiped as a whole column. A Name column of a technical table (Typ, IP, Version next to it) is a list of resources and stays unless the table has a mail or a phone column |
| `awb import tcp-xxxx --paste` (no kind) | plain text: the copy is `paste-<date>-<n>.md`, signatures and quoted headers are wiped as for a mail, nothing else is added |
| `awb register keep "phrase"` | a term that was wiped by mistake is never wiped again, in any customer's material (then `awb import --redo`) |
| `awb register keep --list` | the kept phrases (vault side only) |
| `awb register add CUST-XXXX CUST "full company name" "short name" ...` | register one or more written forms of a code in one call (one bad form and nothing is added); add every short form too. `-` alone reads the forms from standard input, one per line; `awb import` asks for the forms of a new customer itself |
| `awb register find words of a form` | the code and the kind of the entry whose form is these words, exact after the folding of the matcher (case, umlauts, whitespace), or `no code`; owner's own terminal only: refused with one fixed line in a pipe, as the work user and inside an assistant session, as `awb vault show` is. It never prints a form, a near miss or a count |
| `awb register new CUST` or `PART` | print a fresh code; `PERS`, `ORG` and `SITE` codes come from `--review` only |
| `awb register list` | codes, kinds and counts of forms, no names |
| `awb register list --forms` | the same with the written forms (vault side only) |
| `awb register retire CUST-XXXX` | retire every form of a code; the code is never reused |
| `awb words update [--root DIR]` | rebuild `rules/known-words.txt` and `rules/known-phrases.txt` (the capitalised words and two-word phrases of the public mirrors, which the intake reads as terms) after `awb mirror docs` or a new service description; `--root` names the mirror root (default `AWB_MIRRORS` or `~/tcp-mirrors`) |
| `awb images list [CUST-XXXX]` | the pictures the intake held on the vault side (office media, pdf images, image files), per file: held, released, left out |
| `awb images release CUST-XXXX FILEID N...` | after you looked at them: copy the chosen pictures to `~/tcp-shared/outbox/CUST-XXXX/images/`; `--all` for every held picture of the file |
| `awb reveal FILE --out PATH [--replace]` | put the real names back into a finished text: every code becomes its first active form; the named file gets mode 600 and never goes where a session reads; `--replace` overwrites an existing output file |
| `awb fetch tcp-xxxx [--again] [--into DIR]` | what the project put with `awb xchg put` since your last fetch: each file of `<code>/from-session/` of the lab bucket downloaded through the key service (the same list and get a session's `awb xchg list` uses) into `~/awb-fetch/tcp-xxxx/` (mode 700, files mode 600; `--into` names another folder), the real names put back into every text as `awb reveal` does, a file that is not a text kept as it came, then the folder printed. A file counts as fetched once downloaded (its key in `bucket-pulled.tsv` of the vault); `--again` takes all again. Refused inside a git tree and where a session reads. The objects stay in the bucket (`awb xchg clean` in the session deletes them). Your own terminal only |
| `awb vault status` | state of the vault: plain, locked or unlocked, with the count of codes and forms |
| `awb vault encrypt [--stdin]` | encrypt the vault once (new passphrase twice), then unlock; `--stdin` reads the passphrase twice from standard input |
| `awb vault unlock [--stdin]` | give the passphrase to the vault daemon, after every reboot; `--stdin` reads it from standard input |
| `awb vault lock` | drop the passphrase and the register from the daemon's memory |
| `awb vault reload` | hand the vault daemon to a new process of the installed code without a lock (what `awb deploy` and `systemctl reload awb-vaultd.service` run): `vault <state>, pid <n>, release <commit>`. While it runs, a write to the vault (unlock, lock, a register save, a seal) answers `busy`: the vault daemon is reloading, try again. A stop, a crash or a reboot still lock the vault |

Every import first runs its self-test over the planted cases of `awb/planted.py` and takes nothing in when one of
them is no longer found, when a planted name of the wipe cases comes out unwiped, when a control term is wiped or
when the customer inside a company shape does not become the code. Every output passes the final check: the matcher,
the structured patterns and the candidate rules over its body, and a second check by another method (the letters of
whole words against every registered form and every form the run learned). A file that fails it is withheld and its
original stays in the inbox. What the rules do not recognise passes: a first name alone in prose, a name only glued
into an identifier, a name in a picture (the pictures stay held, `awb images`).

The pieces behind `awb import`, one line each:

| command | what it does |
|---|---|
| `awb intake --customer CUST-XXXX [--review] [FILE...]` | the intake alone, in wipe mode (no FILE: the vault inbox; `--customer new` issues a random code) |
| `awb bucket pull CODE` | new files of `in/` into the vault inbox, then the intake |
| `awb register review CUST-XXXX [--report REPORT]` | the review of the newest stop of `--review` by hand; `--report` names another private report of the customer |

## The laptop (`awb clean`, Ubuntu under WSL)

The anonymization before the host, on your own laptop, offline. No vault daemon, no key service, no work user. The
customer of a project is `CUST-` and its four characters.

| command | what it does |
|---|---|
| `awb init --laptop` or `awb clean init` | `~/awb-laptop` (or `AWB_LAPTOP_HOME`) with `vault/` (700), an empty register and `tmp/`; while the PATH and proxy lines of the shell are missing the last line names `awb clean shell` |
| `awb clean shell` | the PATH line of `~/.local/bin` and the source line of `~/.config/winrelay.sh` (both guarded, a second run changes nothing): a marked block at the end of `~/.bashrc` (left as it is when it already has both); when `~/.oh-my-zsh` exists the file `${ZSH_CUSTOM:-$HOME/.oh-my-zsh/custom}/awb.zsh`, which oh-my-zsh reads after `~/.zshrc`. `~/.zshrc` is never touched: oh-my-zsh replaces it on install and lines added there are lost. Open a new terminal after it |
| `awb clean use tcp-xxxx` | names the project once: it becomes the current project of the laptop (`~/awb-laptop/project`) and its work folder `~/work/tcp-xxxx` is made (`AWB_WORK_HOME` names another root; with a layout root `clean/` of `<root>/YYYY-MM/tcp-xxxx/`, see `awb clean layout`); without a code it prints the current one. Every later `awb clean`, `put` and `fetch` takes `--project` first, then the project whose work folder holds the current directory (or a folder below it), then this one, and prints `project: tcp-xxxx (from ...), customer CUST-XXXX` as its first line |
| `awb clean register CUST-XXXX` | the written forms of the customer, typed once on the terminal, one per line, an empty line ends (an empty first line: no form); nothing is echoed; they stay in the laptop's vault folder |
| `awb clean FILE... [--project tcp-xxxx] [--kind docs\|logs] [--out DIR]` | the default kind is logs for a file ending in `.log` and docs for every other file (a call with both makes one run and one report each; the chosen kind is printed); without `--project` the copies go into `clean/` of the work folder, with it into `./clean/`; a Windows path (`D:\Documents\x.docx` or `D:/Documents/x.docx`) is read as `/mnt/d/Documents/x.docx`; a customer not registered on the laptop yet is asked for once on the terminal as `awb clean register` asks (no terminal: refused with the register line); the last line names `awb clean put` |
| `--kind docs` | documents (docx, pptx, xlsx, odt, pdf, Markdown, text, html, mail): the body text with the customer as its code and every other person, company, place, mail address, phone and secret as a token (a secret is also a password written in prose after a password word, the words around it stay); pictures, properties, headers, footers and comments left out; one `<name>.clean.md` each in `./clean/` or `--out` |
| `--kind logs` | logs, configs and tickets: users, hosts, IP addresses, mail addresses, phones, keys, tokens and passwords wiped, no name guessed, the technical words kept; one `<name>.clean.<suffix>` each |
| `--put` | the clean copies (never the originals) into `<YYYY-MM>/tcp-xxxx/in/` of the bucket `awb` with your own key in `AWB_OBS_AK` and `AWB_OBS_SK`; the folder under any month, else a new one under this month; a name already in `in/` is not replaced |
| `awb clean put [--project tcp-xxxx]` | sends the clean copies of the last run of the project (the rows in state clean of its reports) into `in/` as `--put` does, without cleaning again |
| `awb clean serve [--port 8765]` | the same flow as a local page: it listens on 127.0.0.1 only and prints `http://localhost:8765/?t=TOKEN` to open in the Windows browser (WSL forwards localhost). The token is new per start and every request carries it; a Host header other than localhost or 127.0.0.1 is refused. The page: the project (prefilled, a button use), files to upload or Windows paths to type, the kind (auto, docs, logs), run (into `~/work/tcp-xxxx/clean/`, then the report and a link per clean copy that opens it as text) and put (needs `AWB_OBS_AK` and `AWB_OBS_SK` in the environment of the serve process: `set -a; . ~/awb-laptop/obs.env; set +a` before the start). Uploaded originals go into a temporary folder (700) that is deleted after the run; no file content is logged. No marking of names, no editor, no review step. Ctrl-C ends it |
| `awb clean doctor` | the proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` in both cases, the host and port only, never a user or a password), then one HEAD request through the environment's proxy to the object storage of the region and to github.com (no file, nothing of yours); a failure names its fix: the proxy cannot be reached, the proxy wants a login, or TLS verification failed (install the root certificate of a TLS-inspecting proxy with `update-ca-certificates`, then `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` if Python does not pick it up). One more line names the command that fixes the shell: zsh with oh-my-zsh and no `awb.zsh` (`awb clean shell`, then a new terminal), or `HTTPS_PROXY` unset while `~/.config/winrelay.sh` exists (`. ~/.config/winrelay.sh`). Exit 1 when a target fails |
| `awb clean fetch [tcp-xxxx] [--to DIR] [--save] [--again NAME]` | the finished files of `<YYYY-MM>/tcp-xxxx/out/` (the real names back, put there on the host with `awb bucket put CODE FILE --reveal`, which ends with the line `get it: Total Commander, bucket awb, folder <YYYY-MM>/tcp-xxxx/out/, or on the laptop: awb clean fetch tcp-xxxx`) into DIR, or the folder saved before with `--to DIR --save` (for example `/mnt/c/Users/<you>/...`); your key in `AWB_OBS_AK` and `AWB_OBS_SK`, through `HTTPS_PROXY` like `--put`; one line per file (fetched, already fetched, failed); the etags are remembered in `~/awb-laptop/vault/fetched.tsv` and a recorded file is not fetched again; `--again NAME` (repeatable, NAME is the file name in `out/`) fetches it again all the same, and a local file of that name stays: the new one gets ` (2)`; a NAME that `out/` lacks is named and counts as failed; `in/` is never touched. A Markdown deliverable comes as md and HTML; the line after the HTML names its Windows path (`C:\Users\<you>\...`) to open it, select all and paste into a mail. A Windows `--to` (`C:\Users\<you>\Downloads`) is read as `/mnt/c/Users/<you>/Downloads`. Exit 1 when a download failed |
| `awb clean report [--dir DIR] [--save]` | the codes file of the report workbook: downloads `reports/projects.csv` and `reports/projects.meta.json` of the bucket (put there on the host by `awb report --codes --put`) with your key in `AWB_OBS_AK` and `AWB_OBS_SK`, through `HTTPS_PROXY` like `awb clean fetch`; checks the sha256 of the sidecar (a mismatch replaces nothing), keeps the file before as `projects.previous.csv` and replaces `projects.csv` in one step (written as `projects.csv.part`, moved over the old one, three tries two seconds apart while Excel holds it, else `Excel holds the file, run it again` and exit 1). The sidecar is read and never written. It prints `projects.csv: 6 rows, 1 text withheld, written 2026-10-29 07:50 UTC (2 h old), replaced. In Excel: Data > Refresh All or open report.xlsx.` The folder is given once with `--dir "C:\Users\<you>\awb-report" --save` (kept in `~/awb-laptop/report-dir`). It never uploads |
| `awb clean inventory ROOT... [--project tcp-xxxx] [--label LABEL] [--put] [--include-onedrive]` | the files under the folders you name, without their content, for the move plan (a Windows path `D:\Kunden` is read as `/mnt/d/Kunden`). A file is opened only to hash it (sha256 and md5) and, for the fingerprint of the report workbook, to read `xl/workbook.xml`. The full list with the real paths goes to `~/awb-laptop/vault/inventory/<stamp>.tsv` (600, this laptop only); the coded copy to `~/awb-laptop/inventory/laptop-<stamp>.tsv` (`laptop-<stamp>-<label>.tsv` with a label) with the eleven columns of `awb/inventory.py`: id, path, suffix, size, mtime (UTC), sha256, md5, project (`none` without `--project`), group, rank, place. Every path segment relative to its root goes through the name machinery of `awb clean` (a registered form becomes the customer code, another person or company a token like `person-1`); a path that still carries something, also across segments read together, is `[withheld]` with its id, size and hashes. With several roots a path starts with `root1/`, `root2/`; the roots stay on the laptop. The label is checked like a path and refused when it carries a name. Skipped and counted: the report folder, a workbook with both sheets Names and Projects, the laptop folder, `_archive` and `.git` folders, `~$` files, `.tmp` files, `Thumbs.db`, `desktop.ini` and links. A root in the report folder is refused, one under OneDrive too without `--include-onedrive` (hashing would download cloud-only files). `--put` sends the coded copy alone to `reports/inventory/` of the bucket with your key and proxy, like `awb clean put`; a file of that name there is not replaced |
| `awb clean layout [ROOT] [--save]` | sets the layout root once (a Windows path `D:\Work` is read as `/mnt/d/Work`, kept in `~/awb-laptop/layout-root`); replacing one set before needs `--save`; without ROOT it prints the one set. A root in the report folder or the laptop folder is refused. After it a project lives in `<root>/YYYY-MM/tcp-xxxx/` with `private/`, `clean/`, `out/` and `_archive/`: `awb clean use tcp-xxxx [--month YYYY-MM]` makes `private/`, `clean/` and `out/` and takes `clean/` as the work folder (the month of the folder found under the root, else `--month`, else that of the project's bucket folder when your key is set, else this month), `awb clean FILE` writes its copies there and `awb clean fetch` without `--to` lands in `out/`. The folders under `~/work` stay where they are |
| `awb clean files plan [STAMP\|latest]` | fetches `reports/plan/<stamp>/PLAN.tsv` of the bucket (the newest by default, made on the host by `awb files plan --put`) with your key through the proxy, keeps it in `~/awb-laptop/vault/plans/<stamp>.tsv` (600) and prints each move and archive with the real old and new path, joined by id with the full local inventories of `awb clean inventory`; this screen only, nothing is sent. A row whose id is not in a local inventory or whose target is not a layout folder is named. Exit 1 when one is |
| `awb clean files apply [STAMP] [--go] [--include-onedrive]` | the plan fetched last: without `--go` the dry run (what would move, what is skipped, nothing changed); with `--go` the moves into the layout root, `move` to `YYYY-MM/tcp-xxxx/private\|clean\|out/` plus the file name, `archive` to `.../_archive/<stamp>/` plus the path relative to the inventory root. Nothing is deleted or overwritten (a taken name gets ` (2)`); a file whose size or sha256 differ from the inventory, a missing one, one outside its inventory root, a new place outside the layout root, the report folder, the laptop folder, the report workbook and OneDrive without the flag are skipped with the reason. Each move goes into the undo journal `~/awb-laptop/vault/moves/<stamp>.tsv` (600). Exit 1 when something was skipped |
| `awb clean files undo [STAMP]` | moves every file of the journal (default the newest) back to its old path when it still has its sha256 and without overwriting; the journal is kept as `<stamp>.undone-<time>.tsv` |
| `awb clean update` | the newest lists of public words from github.com/shimoza/tcp-awb (`git pull --ff-only` of the clone, or a download checked against the blob ids of the tree); prints what changed in counts and sends nothing of your files |

Each run writes `clean-report-<stamp>.md` (kinds and counts per file, never a value) into the output folder and the
mapping of tokens and values into `~/awb-laptop/vault/maps/tcp-xxxx/`. A copy that fails the final check of the
intake is not written. On the host `awb import --auto` takes the copies in.

The report workbook never leaves the laptop (`rules/report-workbook.txt`). `awb clean FILE`, `--put`, `awb clean put` and the page of `awb clean serve` refuse a file in the report folder (the folder saved with `awb clean report --dir DIR --save` or any folder named `awb-report`) and any workbook with both sheets Names and Projects, whatever its suffix, with the one line `the report workbook never leaves the laptop`; `awb clean fetch --to` refuses the report folder. On the host `awb import` and `awb import --auto` hold such a workbook: nothing of it is imported, it stays in `in/`, the run says `file N of M held: ...` and you get one mail per file to delete it there.

### Laptop flow

One file of a new project, before LC4: three commands with the project code typed four times and the file path
twice (`awb clean register CUST-XXXX`; `mkdir -p ~/work/tcp-xxxx && cd ~/work/tcp-xxxx && awb clean FILE --project
tcp-xxxx --kind docs && cat clean/clean-report-*.md`; `awb clean FILE --project tcp-xxxx --kind docs --out clean-put
--put`). After: three short commands with the code once and the path once, no mkdir, no cd, no cat, no second
cleaning:

    awb clean use tcp-xxxx
    awb clean "D:\Documents\req1.docx"      # asks the forms once if the customer is new, prints the summary
    awb clean put

Or one command, `awb clean serve`, and the rest in the browser.

`sudo seal/verify.sh` (every line PASS).

## The build queue (owner side, presentations/self-build)

A build task is a block in `build/queue/QUEUE.md` of your working copy (untracked) and a prompt file beside it.
The runner (`awb build serve`, step SB3) reads the queue and never writes it but `build/queue/FLAKY.md`; its records are
`/srv/awb-build/runs/<ID>/<n>/`, owner 700: `task.md` and `prompt.txt` (the snapshot at the start), `result.json`,
`session`, `deadline`, `ended`, `task.bundle`, `status.txt`, `checks.log` (one line per check), `suite.log`,
`result.md` (fixed fields), `message.txt` (the agent's text, for `awb build show` alone), `commit`, `mail`, `state`,
`flaky.txt` (the nodes that passed on the rerun), `widen.log`.

When the whole suite of a task or of `awb build check` has failures, the failed nodes alone run once more in the same
suite unit on the same tree (at most 20 nodes; more is a broad failure and gets no rerun). When they all pass, check 9
passes with a line `flaky: NODE...` in `checks.log` and `result.md`; a node that fails again is `red: suite`. The
baseline and the task's own check never rerun; the hollow-test check is never rerun either: a test that is gone or
skipped stays `red: tests lost`. `runs/.flaky.tsv` keeps a row per flaky node; a node flaky a second time in seven
days adds a line to `build/queue/FLAKY.md`, which the steering session reads. A node id the gate or the plain form
of a test id refuses is written as `(node withheld)`.

|---|---|
| `awb build add FILE` | a task into the queue. FILE holds the block (`## B-012: title`, then `key: value` lines; `model`, `effort`, `budget` and `clock` may be left out, `prompt` and `end` are written for you), a line `---` and the prompt. The grammar and the gate's classes with the register run first (a refusal names the key or the class and the line, never the value); then `build/queue/B-012.md` and `QUEUE.md` are each written to a fresh name and renamed, so a reader sees the old queue or the new one. Refused when the id is in the queue or has a run and when the name check cannot run. A block that lists an always allowed file (`README.md`, `CHANGELOG.md`, `COMMANDS.md`, `INTERFACES.md`, `build/tests.json`) is added with a warning on stderr: every task may change those files, so they reserve no path |
| `awb build draft FINDING [--from FILE] [--id B-NNN] [--out FILE]` | in the root of your working copy: an add file for `awb build add` from a row of a findings table, so the steering session writes no task by hand. ## The egress filter of the work user (seal/egress/ALLOW.md)

| command | what it does |
|---|---|
| `awb egress status [--json]` | any user: the mode, when the table was loaded and refreshed, and per class what the last 24 hours counted outside the list (`allowed` counts the connections to the list) |
| `sudo awb egress load` | root: resolve the host names of `seal/egress/ALLOW.md`, load the table `inet awb_egress` in the mode of `/etc/awb/paths.conf` or refresh its address sets in place, record the counters. `seal/setup.sh`, `awb-egress.service` at boot and `awb-egress.timer` every 5 minutes run it |
| `sudo awb egress enforce [--accept CLASS...]` | your own shell: refuse every connection of the work user outside the list, also one opened while the filter counted (its packets lack the mark of the allow rules) and the answers of a listener to an inbound connection. With `conntrack` installed it deletes the conntrack entries of those connections (mark `0xa0b002`) and says how many; without it says so and the filter refuses their packets all the same. Refused (exit 1, the mode stays count) unless the last 24 hours were counted without a gap of more than 30 minutes and no class counted a connection but `probe` (the planted one of `seal/verify.sh`) and the classes you name with `--accept` because you expect to lose them |
| `sudo awb egress count` | your own shell: back to counting, nothing refused; the 24 hours start again |

The mode is the line `egress = count|enforce` of `/etc/awb/paths.conf` (count when it is missing); the setup writes
count and keeps what it finds. The classes: `probe`, `metadata`, `dns`, `ntp`, `tcp_api`, `github`, `ssh`, `mail`,
`web`, `other_tcp`, `other_udp`, `icmp`, `other` (`seal/egress/ALLOW.md` says what each holds).

## The price workbook

`awb pricebook` builds one workbook per estimate from a specification file with live prices and compares versions. It
needs no key and no vault, so sessions run it. Runtime code is the standard library only.

| command | what it does |
|---|---|
| `awb pricebook build SPEC [--out FILE] [--lang en\|de] [--against OLD] [--no-record] [--project DIR]` | refuses a service the service description does not offer (before any price call), asks the public price API once per region, prices every line from the record it found and writes `FILE.xlsx` (default: the specification with the ending `.xlsx`) and a Markdown summary `FILE.md` for a mail. Nothing is written unless every line is priced. `--lang` picks the headers, the fixed texts and the number format of the summary (default: `language:` of the specification, else en). `--against OLD` (a workbook or a specification) adds the sheet of changes. The two totals are recorded with `awb calc` when the specification lies in a project, so the review takes them with `calc:K-N` (`--no-record` leaves that out). Exit 0 done, 1 a line refused (nothing written), 2 the price API did not answer, a bad specification or an error |
| `awb pricebook diff OLD NEW [--lang en\|de] [--no-prices]` | what changed between two specifications, two workbooks or one of each, line by line (matched by item name) and in the totals. A specification is priced now, both versions against the same snapshot; `--no-prices` compares the settings of the lines only. Exit 0 no difference, 1 a difference, 2 the price API did not answer or an error |

A specification is a text file (or JSON) that a person can read. Settings at the top (`title`, `region`,
`language`), then one block per line item, headed by its name in square brackets. A line starting with `#` is a
comment and a line starting with a blank continues the key above.

```
title: Sizing for CUST-Q7M4
region: eu-de
language: en

[web servers]
service: ecs
flavor: s3.large.2
os: Open Linux
quantity: 4
mode: payg
assumption: Two zones and all day.
assumption.de: Zwei Zonen und rund um die Uhr.

[data disks]
service: evs
flavor: vss.ssd
quantity: 2000
assumption: 500 GB per server.
```

| key | meaning |
|---|---|
| `service` | the service as the service description or the price API names it (`ecs`, `Elastic Cloud Server`); it is checked against the service description |
| `api` | the price API service when it is not the same (`ecsflex` under ECS); needed when `service` is not written like an API name. A name in `rules/services-not-offered.txt` or a withdrawn section is refused here too |
| `flavor`, `os` | the record: `os` is the OS unit (`Open Linux`) or a part of it that fits one record only (`Linux` alone fits four of them); it is needed when the flavor has several OS tiers |
| `id` | the id of a price record, instead of `flavor` and `os` (for records without a flavor and for tiered rates) |
| `region` | `eu-de`, `eu-nl` or `eu-ch2`; the setting at the top is the default, which is `eu-de` |
| `quantity` | a positive number with a decimal point, not a comma |
| `hours` | hours per month, for an hourly rate only; 720 when left out (the public calculator counts 720). Not allowed for a reserved rate or a monthly unit. At most 744 |
| `mode` | `payg` (default), `r12`, `r24`, `r36` (reserved) or `ru12`, `ru24`, `ru36` (reserved, up front); also written `pay as you go`, `reserved 12`, `up front 24` |
| `assumption` | free text per line; `assumption.de` and `assumption.en` replace it in a workbook of that language |

A line needs a unique item name. The JSON form has the same keys in a list `lines` (each with a `label`), with
`assumption_de` for `assumption.de`. At most 120 lines. A specification carries codes (`CUST-Q7M4`), never a name.

The monthly figure of a line is the rate times quantity times hours rounded half up to the cent (a reserved rate is a
flat monthly value, so rate times quantity); the yearly figure is the monthly figure times 12. The workbook has the
sheets Lines, Sources and (with `--against`) Changes, in German Positionen, Quellen and Änderungen. The lines carry
the unit price, quantity, hours, monthly and yearly figure (formulas with their stored results), the assumption in
its own column and the id of the price record. Below them a block of totals holds the monthly and yearly total and the
cells `Months per year` and `Hours per month` that the formulas use. Sources holds the time of the price API
snapshot of each region, the revision of the service description, the section of each service, notes such as a
tiered rate and the recorded calculation ids. A rate in a currency other than EUR is refused.

The name check of `awb kb` (add, amend, recheck, retire, verify, what `find`, `show`, `scope` and `expired` print
and the export that `awb dataset build` reads) lets a registered form pass in one place only: inside the full name
or short name of a service of `rules/services.tsv`, written as the service description writes it (whole phrase,
same case) and longer than the form. A service named like a customer is a fact and stays as it is. The same word
alone, in other case or beside only a part of the service name still hits. `awb register keep` is not the way: it
would let the customer's own material pass. The intake and `awb gate` keep the plain check.

`awb kb` writes files, it never runs git. The knowledge base is your own repository: create it once with
`git init` and give it an identity of its own, because the work user has no global one and a commit fails
without it.

```
cd ~/tcp-kb && git init && git config user.name "Architect Workbench" && git config user.email awb@localhost
```

Then give it the commit gate once: `awb gate --install --kb --repo ~/tcp-kb`. Every commit runs the self-test of the
gate, the gate over what it carries and `awb kb verify --staged`, so a file written around `awb kb` does not get in.

The saved workflow `workflows/review.js` runs the blind checks of tier 2 and 3 first and then the lenses, which see
the blind results; a lens finding without a quote or evidence is dropped and counted, a refute agent that cannot
settle a finding leaves it plausible (soften the sentence, set `softened`). After every fix and the cut to the
budget, `workflows/request-check.js` is the last check (tier 3): where each question is answered, what nobody asked
for, what is stated more firmly than its grade. Both make review level 1, "ревью" or "review": on the session's
own model, without a confirmation, findings only, never a block of a put.

Review level 2, "глубокое ревью" or "deep review" (also "финальная вычитка" or "final check"), is a third
workflow, `workflows/final-check.js`, for a high-stakes deliverable. A project session says the cost in one line
first (one agent on Fable 5.1 at effort max, about 200-300k tokens and 10 to 15 minutes) and runs it after one word
of his. Neither level runs on its own. The agent reads input/, SCOPE.md, STATE.md, OPEN.md,
evidence/, the review folder and the draft, writes the answer again from the request into `deliverables/STEM.final.md`
and the table of questions, caveats, cuts and unsupported claims into `reviews/FILE/final-check.md`; each caveat and
claim says whether it was known from the base before the work (yes/no). The script
records the run in `reviews/FILE/final-check.json` with the sha256 of the final text; `awb review show` lists it.
The final text is a new deliverable with its own review. That review costs less: the session runs
`workflows/review.js` (scriptPath `/opt/tcp-awb/src/workflows/review.js`) with `after_fx: true` in its args, which
runs only the platform lenses and the partner lens, then `awb review pass`. While the final text has the hash of its
record, the pass needs no blind verification and takes the final check for the request check. After
an edit or with a record from before the hash the full review applies again and the messages say so.

A tier 3 pass refuses a blind verification that checked 0 claims while the text has high-risk claims whose verdict no
blind check set: verdicts filled in claims.tsv before the review hide the claims from it. Clear them and run the
review again; review.js stops after its prepare step in that case.

A text in his name follows the drafting skill (`seal/work-claude/skills/drafting/SKILL.md`, installed by the seal
for the work user): facts first (the review above), then the checked version is kept as
`reviews/FILE/before-voice.md`, then the voice pass, `awb write keep`, `awb write check`, the cut to the budget as
a last step and both checks again. After he sends it, `awb voice learn DRAFT SENT`. On the owner side the sent text is piped in instead, `pbpaste | awb voice learn DRAFT -`: it is wiped like a paste and the original is written nowhere.

## Used by the client, not by hand

`awb hook prompt | pre-write | pre-tool | post-write | stop | session-start` are the hooks of working sessions
(`pre-tool` is the tool guard that keeps a session inside its project; a hook that runs over 50 seconds stops itself
and fails closed). `awb hook selftest` plants refused cases and a pass in a throw-away home and exits 1 when a planted refusal passes. While the vault is locked, or the name check cannot run for any
other reason, every prompt of a work session is refused with the time of the lock and the unlock to run, and a
session starts without its project files. `awb vault status`, `awb board` and the 503 of `GET /api/board` open with
`locked since <time>`. `awb vault serve` is the vault daemon under systemd (`--admin-socket` and `--check-socket` name its two sockets).

On a sealed host `/usr/local/bin/awb` is a root owned wrapper that runs `/opt/tcp-awb/venv/bin/python3 -I -m awb`,
so a package in the invoking user's site folder or on `PYTHONPATH` is never loaded ahead of the installed code. A
project gets the hooks of that installed command only: `awb spawn` from the repository environment refuses on a
sealed host (fail closed); run it as the work user.
